# Template DSL

Template DSL определяет, как создаются шаблоны в Templater.

Шаблон — это не просто папка.  
Это **типизированное, версионное определение структуры и поведения проекта**.

В этом документе описаны:

- API `defineTemplate`
- Поддерживаемые поля конфигурации
- Хуки жизненного цикла
- Поведение рендеринга
- Ограничения и гарантии
- Рекомендации
- Политика стабильности

---

## Обзор

Шаблон должен экспортировать конфигурацию по умолчанию через `defineTemplate`:

```ts
import { defineTemplate } from "@templater/core";

export default defineTemplate({
  name: "landing-basic",
  version: "1.0.0"
});
````

Объект конфигурации определяет метаданные, вопросы, источники файлов и хуки жизненного цикла.

---

## Базовая структура

Минимальный пример:

```ts
export default defineTemplate({
  name: "my-template",
  version: "1.0.0",

  questions: [],

  files: {
    source: "files"
  }
});
```

Валидная директория шаблона должна содержать:

* `templater.config.ts`
* директорию с исходниками (по умолчанию: `files/`)

---

## Обязательные поля

### `name: string`

Идентификатор шаблона.

Должен:

* быть уникальным в контексте распространения
* содержать только URL-безопасные символы
* оставаться неизменным между версиями

---

### `version: string`

Версия шаблона.

Должна следовать семантическому версионированию (`MAJOR.MINOR.PATCH`).

Templater пока не принуждает к разрешению версий, но метаданные версии обязательны.

---

## Вопросы

Вопросы определяют ввод пользователя, необходимый при генерации.

Пример:

```ts
questions: [
  {
    type: "input",
    name: "projectName",
    message: "Название проекта",
    default: "my-app"
  },
  {
    type: "select",
    name: "css",
    message: "Решение для CSS",
    options: ["scss", "tailwind"]
  },
  {
    type: "confirm",
    name: "analytics",
    message: "Включить аналитику?",
    default: false
  }
]
```

---

### Поддерживаемые типы (v0.x)

* `input`
* `select`
* `confirm`

Каждый вопрос должен определять:

* `type`
* `name`
* `message`

Опционально:

* `default`
* `validate(value) => boolean | string`

CLI и расширение отвечают за отображение этих вопросов.

Ядро только потребляет готовые ответы.

---

## Конфигурация файлов

Поле `files` определяет директорию-источник шаблона.

```ts
files: {
  source: "files",
  include?: string[],
  exclude?: string[]
}
```

### `source`

Путь относительно корня шаблона.

По умолчанию `"files"`, если не указано.

---

### `include` / `exclude`

Glob-паттерны, определяющие обрабатываемые файлы.

Если не указаны:

* все файлы в `source` считаются обрабатываемыми

---

## Правила рендеринга

Templater рендерит текстовые файлы через движок шаблонов (сейчас Handlebars).

Поддерживаемый синтаксис:

### Переменные

```html
<title>{{projectName}}</title>
```

### Условия

```html
{{#if analytics}}
<script src="analytics.js"></script>
{{/if}}
```

---

## Бинарные файлы

Бинарные файлы автоматически определяются и копируются без рендеринга.

Это гарантирует сохранность:

* изображений
* шрифтов
* медиа-ресурсов

---

## Хуки жизненного цикла

Шаблоны могут определять хуки:

```ts
hooks: {
  beforeGenerate(ctx) {},
  afterGenerate(ctx) {}
}
```

Хуки опциональны.

---

### Модель выполнения хуков

Хуки выполняются в ограниченном `TemplateContext`.

Концептуально:

```ts
interface TemplateContext {
  vars: Record<string, any>;
  log(message: string): void;
  write(path: string, content: string): Promise<void>;
  remove(path: string): Promise<void>;
  exec(command: string): Promise<void>;
}
```

Важно:

* Хуки не должны полагаться на прямой доступ к файловой системе.
* Все операции записи ограничены целевой директорией.
* `exec` может быть отключён в безопасном режиме.

Хуки должны быть детерминированными и идемпотентными.

---

## Генерация метаданных

После генерации Templater создаёт:

```
.templater/meta.json
```

Содержит:

* имя шаблона
* версию шаблона
* временную метку генерации

Шаблоны не должны переопределять этот файл.

---

## Детерминизм

Шаблоны должны быть детерминированными.

При одинаковых:

* версии шаблона
* входных данных
* политике записи

Результат должен быть идентичным.

Шаблоны, использующие:

* случайность
* внешние API
* значения, зависящие от времени

настоятельно не рекомендуются.

---

## Политика стабильности

Template DSL будет развиваться осторожно.

Правила:

* Критические изменения требуют инкремента мажорной версии.
* Устаревшие поля остаются поддерживаемыми в 0.x с предупреждениями.
* Стабильность DSL необходима до выхода `1.0.0`.

---

## Рекомендации

### 1. Держите шаблоны минимальными

Избегайте встраивания:

* полных node_modules
* крупных сгенерированных артефактов

---

### 2. Избегайте побочных эффектов в конфиге

`templater.config.ts` не должен:

* выполнять команды при импорте
* изменять глобальное состояние

---

### 3. Предпочитайте явное неявному

Избегайте угадывания поведения внутри хуков.

---

### 4. Версионируйте осознанно

Если вывод шаблона изменился:

* увеличьте версию
* задокументируйте изменения

---

### 5. Держите вопросы сфокусированными

Избегайте избыточной конфигурации.  
Шаблоны должны направлять, а не перегружать.

---

## Анти-паттерны

Избегайте:

* динамических импортов на основе ответов в рантайме
* записи вне целевой директории
* использования хуков как полноценных генераторов проектов
* перегрузки шаблонов поведением, зависящим от окружения

Templater — движок для каркасов проектов, а не инструмент развёртывания.

---

## Запланированные расширения

Пока не реализовано, но архитектурно поддерживается:

* Feature packs (`templater apply`)
* Композиция шаблонов (`extends`)
* Условные деревья файлов
* Интеграция метаданных реестра

---

## Итог

Template DSL существует для баланса между:

* мощностью
* безопасностью
* предсказуемостью
* удобством разработки

Шаблоны должны ощущаться структурированными, а не магическими.

Templater спроектирован для масштабирования от небольших лендингов до структурированных экосистем — без потери ясности.
